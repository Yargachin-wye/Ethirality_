# План: таблица лидеров, защита результатов и версии

Статус: предложение к реализации, 12 ноября 2026. Игровой код пока не изменён.
Цель: общий рейтинг игроков, в котором сравниваются результаты по одинаковым правилам,
а редактирование сохранения или отправка произвольного числа не дают место в топе.

## 1. Что есть в проекте

- `SaveSystem` хранит HP, улучшения и `currentDifficulty` в локальном `savegame.json`.
  `Validate()` пуст, `HandleVersionMigration()` только сравнивает версию с `Application.version`.
  Эти данные нельзя считать доказательством честного результата.
- `Stats.Init()` берёт HP игрока из сохранения; улучшения тоже связаны с `SaveSystem`.
  Рейтинговый старт должен получать собственное начальное состояние.
- `GameplayManager.OnGameOver()` сбрасывает сохранение после смерти.
  Результат нужно зафиксировать при завершении забега, до сброса и выгрузки сцены.
- `GeneratorsManager` строит бесконечный мир по seed и генерирует слои впереди игрока.
  Количество созданных слоёв нельзя использовать как число пройденных.
- `ChoosingNextLevelPanel` запускает как OpenWorld, так и обычные уровни.
  `StartRoundEvent` публикуется после загрузки сцены: параметры рейтинговой сессии
  нужно передать до запуска генерации и появления игрока.
- В проекте есть `Physics2D`, таймеры и вызовы `UnityEngine.Random` в игровом поведении,
  выборе улучшений и эффектах. Воспроизводимость всего забега по seed пока не установлена.
- В игровых скриптах не найдена готовая система очков, аккаунтов и серверного рейтинга.
  В `ProjectSettings.asset` сейчас `bundleVersion: 1.0`.

## 2. Предлагаемые правила первой версии

Это исходные продуктовые решения, которые нужно подтвердить перед реализацией:

1. Рейтинг только для OpenWorld; обычные уровни остаются отдельным режимом.
2. Главная метрика — максимальная высота над стартом за один забег:
   `floor(max(0, maxY - startY) * 100)` в целых сотых игровой единицы.
   Сервер вычисляет окончательное значение из проверенного прохождения.
3. Один лучший подтверждённый результат на аккаунт и таблицу.
   Одинаковая высота даёт одинаковое место; время принятия и ID обеспечивают
   стабильный порядок отображения, но не преимущество в месте.
4. Одинаковые стартовые HP и улучшения; локальный прогресс не переносится.
   Для первой версии — один заданный сервером seed на таблицу, чтобы условия совпадали.
   Смена seed создаёт новую таблицу. Разнообразные seed можно позже оформить отдельным режимом.
5. Рейтинговый забег требует соединения при старте и регулярной отправки данных.
   Офлайн-игра доступна как обычный режим, её результаты не импортируются в рейтинг.
6. В первой версии нет продолжения рейтингового забега из локального сохранения.
   Смерть или добровольное завершение фиксируют результат; перезапуск начинает новую сессию.
   При аварийном закрытии нельзя заявить непереданный прогресс.
7. Допустимый перерыв связи, длительность пауз и максимальную длину сессии определить
   по измерениям на целевых устройствах. До истечения серверного срока можно дослать
   буфер; после — забег продолжается только как обычный. Сбой сети сам по себе не повод для бана.

Не использовать `currentDifficulty` как рекорд: это прогресс выбора уровней, а не высота OpenWorld.
Достигнутый слой можно показывать дополнительной статистикой по фактическому положению игрока.

## 3. Привязка к версии

По умолчанию каждая публичная версия получает отдельную таблицу.
Например, результаты `1.1.0` и `1.2.0` никогда не сравниваются и не переносятся автоматически.

Разделить идентификаторы:

| Поле | Назначение |
|---|---|
| `gameVersion` | Версия для игрока, соответствует `Application.version` |
| `buildId` | Уникальная сборка, назначается процессом выпуска |
| `rulesetId` | Неизменяемая ревизия геймплея, генерации, баланса, подсчёта и параметров физики |
| `protocolVersion` | Формат запросов и журнала забега |
| `saveSchemaVersion` | Формат локального сохранения, отдельный от рейтинга |
| `leaderboardId` | Серверный ID таблицы: версия + ruleset + режим + набор seed |

Сервер хранит реестр разрешённых сборок и сам выбирает таблицу при старте сессии.
Клиент не назначает себе `leaderboardId` при отправке результата.
В сессии навсегда фиксируются версия, ruleset и seed; обновление игры не переносит
начатый забег в новую таблицу. После обновления для нового рейтинга нужен новый старт.

Состояния таблицы: `open` → `closing` → `archived`.
В `closing` запрещены новые старты, но уже начатые сессии принимаются до указанного срока.
Архив доступен для чтения; отзыв читерского результата остаётся возможен с записью в аудит.
Уязвимую сборку можно отозвать немедленно, отдельно от обычного закрытия версии.

Процесс выпуска создаёт манифест сборки и хеш игрового контента, регистрирует
правила на сервере и сохраняет соответствующий валидатор. Обновление баланса внутри
уже опубликованного ruleset запрещено. В манифест входят не только C#-файлы,
но и игровые префабы, ScriptableObject, сцены и настройки физики.
Проверять согласованность `LayerDefinition` в `OpenWorld.unity` и
`Assets/Infos/Balance/OpenWorld.asset`, как требует `AGENTS.md`.

Заявленная клиентом версия или хеш не доказывают подлинность программы.
Подмена этих строк не должна давать преимущество: сервер проверяет прохождение
по закреплённым правилам. Аттестация платформы, где доступна, служит дополнительным сигналом.

## 4. Архитектура и граница защиты

```text
Unity → авторизация → API рейтинговых сессий → хранилище журналов
                          ↓                         ↓
                       база данных ← очередь → валидатор прохождения
                          ↓
                  подтверждённая таблица → Unity
```

Практичный исходный вариант для команды с C#: ASP.NET Core, PostgreSQL,
объектное хранилище журналов и отдельный процесс проверки.
Поставщика хостинга выбрать после определения платформы, бюджета и нагрузки.
Можно использовать готовый игровой backend, если он позволяет запретить клиентскую
запись очков и выполнять собственную серверную проверку.

Авторизация — через проверяемый сервером аккаунт платформы или провайдера входа.
Ник является только отображаемым именем. Гостевой вход допустим для прототипа,
но удаление приложения не должно позволять незаметно обходить санкции в публичном рейтинге.

Клиент отправляет действия и данные забега; сервер решает, допустим ли результат.
Ключи администратора, секреты подписи и доступ на запись в рейтинг хранятся только на сервере.
HTTPS и локальное шифрование не делают вычисленные клиентом очки достоверными.

### Два уровня проверки

**Начальный прототип:** сервер выдаёт сессию, проверяет последовательность событий,
время, допустимые улучшения, пределы движения и повторные отправки.
Это убирает простые подделки и ошибки, но правдоподобный выдуманный журнал может пройти.
Такой прототип подходит для закрытого тестирования, а не для заявления о защищённом топе.

**Целевой публичный рейтинг:** сервер независимо исполняет игровые правила
и вычисляет результат. Предпочтительно проверить возможность воспроизведения журнала
ввода в серверной симуляции: HP, столкновения, улучшения, кулдауны, смерть и высоту
получает валидатор, а не принимает на веру из клиентских снимков.
Все результаты проверяются до публикации; кандидаты в топ могут иметь приоритет очереди.

Перед выбором воспроизведения обязателен технический эксперимент:

- Зафиксировать шаг симуляции и порядок обработки ввода; записывать ввод по тикам.
- Разделить игровые и визуальные источники случайности, воспроизводить выбор наград,
  движение врагов, спавн и порядок событий. Пауза должна быть частью протокола.
- Проверить длинные забеги на целевых устройствах и сервере: гарпун, столкновения,
  рывки, улучшения, удаление слоёв. Одинаковый seed мира не гарантирует одинаковую физику.
- Не исправлять расхождения принятием клиентских HP/координат как истины.
  Если физика расходится, вынести рейтинговую симуляцию в воспроизводимое ядро
  либо запускать её на сервере в реальном времени с предсказанием на клиенте.
  Выбор сделать до основной разработки, с измерением задержки и стоимости.

Даже проверка воспроизведения доказывает допустимость действий по правилам,
а не то, что ввод сделал человек без бота или замедления времени для обдумывания.
Для ограничения таких преимуществ нужны серверный темп приёма команд, лимиты пауз,
анализ поведения; наиболее строгий вариант — симуляция на сервере в реальном времени.
Абсолютную защиту от любых видов читов обещать нельзя.

## 5. Жизненный цикл сессии и API

1. `POST /runs/start`: проверить аккаунт, сборку, доступность таблицы и лимиты.
   Создать непредсказуемый `runId`, закрепить владельца, ruleset, seed, начальное
   состояние, срок действия и серверное время. Допускать одну активную
   рейтинговую сессию на аккаунт; повтор старта с тем же ключом возвращает ту же сессию.
2. `POST /runs/{id}/chunks`: принять нумерованные пакеты ввода и событий.
   Проверять владельца, порядок тиков, размер, срок и состояние сессии.
   Идентичные повторы безопасны; замена уже принятого пакета запрещена.
   Сервер сохраняет время получения; хеш-цепочка полезна для целостности, но не доказывает честность.
3. `POST /runs/{id}/finish`: атомарно закрыть приём новых данных после получения
   полного журнала, поставить проверку в очередь. Повтор возвращает тот же результат.
   Клиентская максимальная высота может быть диагностикой, но не итоговым счётом.
4. Валидатор: `pending → verified / rejected / review`.
   Только `verified` обновляет личный рекорд в транзакции.
   Ошибка инфраструктуры вызывает повтор проверки, а не обвинение игрока.
5. `GET /runs/{id}`: статус и понятная причина отказа/ожидания.
   `GET /leaderboards`: доступные версии; чтение топа и окружения своего места
   с пагинацией, ограничением частоты и кешированием.

Минимальные сущности: `Player`, `Build`, `Ruleset`, `Leaderboard`, `Run`,
`RunChunk`, `LeaderboardEntry`, `ModerationAction`.
Уникальность `(leaderboardId, playerId)` и атомарное сравнение рекорда защищают от гонок.
`Run` хранит ссылку на журнал, версию валидатора, статус, причину и вычисленный счёт.
При удалении рекорда пересчитывать лучший результат из остальных подтверждённых забегов.
Заранее установить срок хранения журналов, объём на аккаунт и максимальный размер сессии.

Дополнительная защита: ограничения частоты/размера запросов, запрет доступа к чужим
сессиям, проверка чисел и диапазонов, отсутствие публичного API записи очков,
журнал модерации и возможность исключить результат или аккаунт.
IL2CPP и обфускация могут повысить стоимость взлома клиента, но не заменяют валидатор.
Автобан по единственному необычному прыжку или рассинхронизации не применять.

## 6. Точки интеграции в Unity

| Место | Планируемое изменение |
|---|---|
| Новые `RankedRunService`, `RunRecorder`, `LeaderboardClient` | Жизненный цикл сессии, сбор ввода, отправка и получение статусов; сеть вне UI |
| `MainMenuPanel`, `ChoosingNextLevelPanel` | Вход, таблица лидеров и отдельный запуск рейтинга после получения сессии |
| `GeneratorsManager`, `PlayerSpawner` | Seed и стартовое состояние из контекста забега до генерации/спавна |
| `Inputer`, `PlayerControllable`, игровой цикл | Ввод, привязанный к шагам симуляции, для независимой проверки |
| `Stats`, `ImprovementsComponent`, `LevelUpPanel` | Отделение состояния рейтинга от `SaveSystem`, воспроизводимые изменения HP и улучшений |
| `GameplayPause` | Явные начало/конец паузы и согласованные серверные ограничения |
| `GameplayManager.OnGameOver` | Однократно завершить запись при смерти до задержки, сброса данных и смены сцены |
| `GameOverPanel` | Высота, личный рекорд, состояния «Проверяется», «Принят», «Не засчитан» |
| Новая панель рейтинга | Топ-100 с постраничной загрузкой, своё место, версия, архив, отсутствие сети и повтор запроса |
| `SaveSystem` | Отдельная версия схемы; локальный кеш не является источником рейтингового прогресса |
| Новый шаг выпуска сборки | Манифест, регистрация версии и проверка согласованности игровых данных |

UI должен показывать версию таблицы и причину недоступности рейтингового старта.
Ожидание сервера не блокирует переход в меню. Повтор отправки после перезапуска
разрешён только для незавершённой серверной сессии и полного проверяемого журнала;
локальный флаг «проверено» никогда не принимается сервером.

## 7. Последовательность реализации и критерии готовности

| Этап | Результат | Когда готов |
|---|---|---|
| 1. Правила рейтинга | Зафиксированы метрика, платформы, вход, seed, паузы, завершение и политика версий | Для одинакового забега нет неоднозначности в месте и принадлежности таблице |
| 2. Эксперимент проверки | Запись ввода и серверное воспроизведение сложного забега; измерены расхождения и ресурсы | Выбран доказуемо работоспособный способ независимого расчёта, либо принято решение о серверной симуляции |
| 3. Backend | Аккаунты, реестр сборок, сессии, журналы, статусы, таблицы и архив | Нельзя записать очки напрямую, использовать чужую сессию или дважды засчитать одну |
| 4. Unity-интеграция | Отдельный рейтинговый старт, запись, завершение, API-клиент | Изменение локального HP/улучшений не даёт преимущества в подтверждённом результате |
| 5. Валидатор | Проверка полного прохождения и вычисление результата по закреплённому ruleset | Поддельные координаты, бессмертие и обход кулдаунов не увеличивают подтверждённый счёт |
| 6. UI и модерация | Топ, своё место, архив, статусы, исключение и восстановление результатов | Игрок понимает состояние результата, оператор может расследовать запись |
| 7. Закрытый тест и выпуск | Проверки атак, сети, обновлений, нагрузки и стоимости | Все публичные записи прошли независимую проверку; настроены мониторинг и отзыв сборки |

Этапы 3–4 можно частично вести параллельно после согласования протокола.
Главная неопределённость объёма работ — серверная проверка текущей физики;
оценивать сроки полного внедрения до этапа 2 было бы ненадёжно.
Первый небольшой объём работ: правила, локальный счётчик высоты и эксперимент записи/проверки,
после него — окончательный выбор backend и оценка ресурсов.

## 8. Проверка перед выпуском

- Правка `savegame.json`, HP, улучшений и позиции в памяти; подмена финального score.
- Телепорт, бесконечное здоровье, уменьшение кулдаунов, изменение скорости игры,
  выдуманный правдоподобный журнал: валидатор должен вычислить результат по своим правилам.
- Повтор пакетов/завершения, нарушение порядка, подмена аккаунта, версии или seed,
  истёкшая сессия, параллельные финиши и повторный запуск процесса проверки.
- Честный длинный забег с паузами, гарпуном, наградами, просадками FPS,
  потерей ответа на finish и восстановлением соединения.
- Версии A/B: раздельные таблицы; закрытие A во время забега; досылка до срока;
  запрет переноса результата в B; отзыв уязвимой сборки и просмотр архива.
- Проверка одинаковых мест, личного рекорда, удаления читерского рекорда
  и корректного восстановления следующего лучшего результата.
- Нагрузка на запись и очередь проверки: задержка подтверждения, стоимость минуты
  симуляции, объём журнала, лимиты хранения и поведение при недоступном backend.
- При изменении баланса/генерации — существующие `BalanceTests` и отчёт по `AGENTS.md`;
  они дополняют тесты рейтинга, но не проверяют честность прохождения.

## 9. Решения, которые нужны от владельца игры

1. Целевые платформы и способ входа: магазин/платформа или отдельный аккаунт.
2. Подходит ли рейтинг OpenWorld по максимальной высоте с одинаковым стартом и seed.
3. Допустимы ли обязательное соединение и отсутствие продолжения рейтинга из локального сейва.
4. Нужно ли защищаться также от ботов/замедления для обдумывания, или главная цель —
   не допускать невозможные по игровым правилам результаты.
5. Бюджет эксплуатации и ожидаемое число одновременных забегов для выбора серверной проверки.
